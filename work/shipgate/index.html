The problem

A coding agent can finish a task and push the wrong thing: a credential from a template file, changes staged by another process, or a commit that cannot be safely undone. Reviewing the working directory alone is insufficient because Git commits the index.

Shipgate puts an explicit policy between an agent's changes and Git. The CLI inspects the staged content, decides whether to ship, block, or wait, and records what happened. The browser simulator exposes that decision without modifying a repository.

What I built

A TypeScript policy library, a Node.js CLI for real repositories, and a browser simulator for inspecting decisions. Repository opt-in, credential findings, destination visibility, external review, and concurrent-agent state feed an explicit result. JSON output lets an agent or CI consume the same decision a person reads in the terminal.

One decision engine, two interfaces

The core library evaluates credentials, destination visibility, busy agents, repository opt-in, and optional external review. The CLI supplies facts from a real repository. The simulator supplies editable, synthetic fixtures to the same planRun function, so the browser can explain the decision without pretending to perform Git operations.

preview reports what the current change would do without staging it. ship stages, scans, applies the policy, commits, and attempts the push. history shows recent commits and whether undo applies. undo uses the recorded commit and remote state, retaining the changes in the working tree.

Key decisions

  1. Scan what Git will commit. The CLI reads staged blobs, including template contents, rather than substituting the working file. A credential-free edit on disk must not conceal a credential still staged in the index.

  2. Make the decision inspectable. Strict, balanced, and yolo policies expose their reasons and explicit overrides. A blocked run names the finding or policy condition. The simulator shows how the same facts change outcome across levels.

  3. Preserve the evidence of a failed push. A successful local commit and a failed remote push are separate outcomes. Recovery must account for the commit that already exists rather than claiming nothing happened.

  4. Bound undo to the observed remote state. Undo uses an explicit force-with-lease expectation. It refuses when origin has moved, instead of overwriting someone else's newer commits.

A credential is not always an API key

The scanner recognizes provider tokens, private keys, JWTs, dotenv filenames, and passwords embedded in database connection URLs. PostgreSQL, MySQL, MongoDB, Redis, AMQP, and SQL Server URLs are covered. Exact placeholders can pass; a real-looking password containing the word “example” does not become exempt.

The same rule definitions drive findings, redaction, the rule reference, and synthetic samples in the simulator. The database URL example places a synthetic password in a template file and blocks it. Tests check that redaction targets the password even when it is identical to the username or URL scheme, and that credential-shaped filenames do not leak into generated commit subjects.

This is a pattern scanner with explicit rules. A clean scan does not establish that a repository contains no secrets, nor does a passing policy prove a code change is correct.

Where recovery gets difficult

Staging is shared mutable state. A blocked operation must restore the index it inherited, and a concurrent operation must not interleave with the transaction. The CLI tests use temporary repositories to check those boundaries, including competing ships and interrupted work.

Undo has a different boundary: another developer may push after Shipgate does. A local record of the last shipped commit is insufficient. The remote lease must match the observed state before an undo can rewrite it; tests deliberately advance origin and require a refusal.

Try the decision

Build the current source and open the browser simulator:

git clone https://github.com/skysssup/shipgate.git
cd shipgate
npm ci
npm run build
npm run dev:web

Choose Password in a database URL, inspect the finding, then compare it with Placeholders in .env.example. The examples contain synthetic credentials. The simulator evaluates policy locally; it does not stage, commit, or push visitor code.

The CLI reference describes setup, repository opt-in, the safety levels, and explicit overrides. Use a disposable repository when trying real commit and undo operations.

Evidence and limits

The repository tests policy decisions, staged-index behavior, real Git transactions in temporary repositories, concurrent runs, failed pushes, undo leases, and simulator parity. Browser tests exercise the production build; package tests install the CLI into an empty consumer.

The useful demonstration is a blocked synthetic credential followed by a clear explanation of what Git would do. Test fixtures establish the modeled behavior, not adoption or customer outcomes. Changes on main can be newer than a published release; the commands above build the current source.
