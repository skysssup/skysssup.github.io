The problem

A tool call can fail after it has already done the work. A payment service creates a refund, the response times out, and an agent retries. Without the same idempotency key, the customer gets refunded twice. The opposite is possible too: a tool returns a convincing success response even though nothing happened, and the agent tells the user the task is finished.

Checking the final answer alone misses both failures. I built AgentCrucible to test the gap between what an agent sees, what it says, and what the service actually changed. It makes those failures repeatable, so a recovery strategy can be checked before it touches a real service.

What I built

AgentCrucible is a TypeScript CLI, library, and local web console. It runs agents against five small services held in memory: payments, email, a database, support tickets, and a filesystem. YAML scenarios describe the task, starting records, faults, allowed changes, and expected outcomes. Fourteen fault kinds cover timeouts, lost responses, stale reads, altered values, malformed results, expired authentication, phantom successes, and duplicate delivery.

The same harness accepts a JavaScript agent module, a model through OpenAI, Anthropic, or Ollama, or an MCP client connected over stdio. Scripted agents run offline without keys. Model responses can be recorded and replayed offline; fresh model calls use the configured provider.

The console brings the evidence together: scenario editing, background runs, a scenario-by-agent result matrix, report timelines, fault sweeps, coverage gaps, comparisons, and reliability trends across agent versions. The CLI writes JSON, HTML, Markdown, and JUnit reports, and a saved baseline can make CI fail when a result regresses or a new scenario fails.

The Northwind workspace shown above is a built-in demonstration, with fictional agents and generated history. It shows how the console works; those numbers are not customer usage or production reliability measurements.

How it works

Each trial starts with fresh worlds and any records declared by the scenario. The agent receives the task, tool schemas, and a callTool function. The harness intercepts each call, applies the selected fault, and records both the real result and the observation delivered to the agent.

Fault timing matters. A fault can stop a call before it runs, change the response after it commits, or deliver the request twice. With timeout_after_commit, the refund exists even though the agent receives an error. With phantom_success, the agent sees a valid-looking result for a call that never ran. The trace preserves that distinction.

The grader compares the world's records before and after the trial, checks invariants after every call, and evaluates the final answer. Every finding points to the relevant call, record, or statement. It returns one of six verdicts: HARMFUL_ACTION, SILENT_FAILURE, DEGRADED, INCONCLUSIVE, SAFE_FAILURE, or SAFE_SUCCESS. The most severe finding decides the trial; the worst trial decides a multi-trial run.

The current refund demo compares five fixed strategies. Blind retry creates two refunds and gets HARMFUL_ACTION; stopping honestly after the timeout gets DEGRADED; reusing the key or checking the committed refund gets SAFE_SUCCESS; claiming success while hiding the error gets SILENT_FAILURE. These are scripted fixtures with known behavior.

A sweep first runs the agent without faults to discover its path, then injects one fault kind at one call per run. Its heat map shows where recovery fails. Saved JSON reports go further: replay reissues the recorded calls against fresh worlds without running the agent, checks each observation and state, then grades the trace again. It can distinguish a changed world from a changed grading rule.

Key decisions

  1. Grade committed state and the answer together. A successful response is not proof of a successful task. SAFE_SUCCESS requires explicit expectations to match. Missing checks or ambiguous evidence can produce INCONCLUSIVE, so an empty finding list cannot silently become a pass.

  2. Make failures repeatable. A seed and a call schedule select the faults. Fresh worlds isolate trials, and reports retain the calls and state changes needed for replay. This makes regressions explainable. Fresh model runs can still vary; recorded model responses provide a repeatable input.

  3. Use explicit grading rules. Expectations, mutation policies, invariants, and typed answer checks produce evidence a developer can inspect. There is no model judging the answer. The tradeoff is that language rules can misread unfamiliar wording, so structured output checks are useful for precise contracts.

  4. Keep the console local and small. The runtime has one dependency, yaml. The browser UI uses TypeScript, escaped HTML, CSS, and SVG charts. Its server binds to loopback by default, checks a session token on API requests, and serves its own scripts and fonts. History stores summaries; complete report files preserve the original trace.

What’s hard

Recovery can repair state without erasing the mistake. In a refund–email–ticket workflow, an agent might create a duplicate refund and later void it, or resolve a ticket before notifying the customer. Checking only the final state loses the intermediate violation. AgentCrucible checks invariants after each call and distinguishes a violation that remains from one that was repaired.

A plausible answer can conceal a missing action. The report below follows a phantom email success. The response looked valid, but the service committed nothing. The final answer still claimed the email was sent, so the grader produced SILENT_FAILURE. The timeline puts the fault, arguments, answer, and committed state in the same place.

Reproducing history is different from retaining a trace. The console keeps compact run summaries and regenerates an old report from its scenario, agent, and seed, reporting whether it matches the stored verdict. If those inputs change, regeneration can differ. A saved JSON report retains the original calls for replay, which still requires deterministic worlds and the same extensions.

Try it locally

With Node.js 22.12 or later, build the current source and run the offline demo:

git clone https://github.com/skysssup/agentcrucible.git
cd agentcrucible
npm ci
npm run build
node dist/cli.js demo
node dist/cli.js ui --demo

Open the local address printed by the console command. --demo creates Northwind in a temporary directory. In a project of your own, init creates a config, starter scenario, and agent module; validate checks the scenarios, run produces reports, and check compares results with declared verdicts or a baseline.

See the console guide, scenario format, model adapters, and MCP setup.

Status and next

This case study describes the v2.1.0 source at commit 475e5c0, checked on 8 October 2026. At that check, the latest published GitHub release was v1.0.0; the commands above build from source. The repository's CI is configured to build, typecheck, run Vitest, exercise documented commands, and verify the package on Node.js 22 and 24.

The main limits are explicit: the worlds are small in-memory mocks without real latency, concurrency, or partial writes; answer parsing uses keyword rules; and answer facts beyond amounts need scenario-specific checks. A safe result applies to the modeled scenario. It does not establish safety against a production service.

The next useful validation is to test a real agent's recovery behavior against scenarios derived from the services it actually uses, then compare those results with controlled integration tests. Richer service behavior and broader answer checks would address the current limits. These are directions for further work, not capabilities claimed by this version.

The grading rules, trace and replay reference, and changelog document the behavior and its boundaries. The project is MIT licensed.
